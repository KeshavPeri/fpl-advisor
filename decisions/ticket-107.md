# Ticket #107 — Record the recommendation inside the override snapshot

## HIGH-IMPACT

- **`registerOverride` now writes a `recommended` object into `recommendation_decisions.snapshot`, alongside the seven existing decided keys, sourced unchanged from the recommendation the confirm panel already compared the entry against — because a ledger entry must be self-contained (everything it could otherwise reference, `recommendations`, is upserted every solver run), and the comparison the decision-history screen needs is only knowable at the moment of registration, when both sides exist together.** This changes the shape of data stored in an append-only ledger, which is expensive to reverse once other code reads it. The seven existing decided keys are unchanged in name, position and value (guarded by a full-object equality test), and rows written before this ticket correctly keep showing the `#103` gap note rather than a fabricated comparison.

- **Scope deviation, made and flagged by the Builder: `src/lib/decisions/api.ts` was edited, though the ticket's file list for the decisions module named only `derive.ts`, `types.ts` and `derive.test.ts`.** Because that file is the one place that remaps the raw `jsonb` snapshot row into the typed shape `derive.ts` consumes, and it was still whitelisting exactly the old seven keys — without extending it, `snapshot.recommended` could never reach the comparison renderer at all, making the ticket's own Scope sentence ("`src/lib/decisions/` renders the comparison when `recommended` is present") unachievable. The fix is narrow, additive and read-only: one new optional field mapped through with the same `?? null` normalization already used elsewhere in the file, plus widening the player-name id lookup to include the recommended side's ids so both sides of the comparison can render names. No other file outside the ticket's list, and none of the ticket's explicit exclusions (`scripts/`, `supabase/`, `commit/`, `reasoning/`, `projection/`, `VerdictCard.tsx`, any migration), were touched.

## ROUTINE

- `OverrideRecommendation` gained a `hitCost` field (read from `recommendations.hit_cost`, which is `NOT NULL` in the schema) solely so `registerOverride` can thread it into `snapshot.recommended.hit_cost` — the confirm panel itself does not display it, and the top-level decided `hit_cost` stays the literal `null` it always was, per the ticket's existing Notes on why a hit is never hand-typed at override time.
- `OverrideScreen.tsx` needed no change: `buildOverrideTarget(recommendation, entry)` in `src/lib/override/derive.ts` already receives the full recommendation object, so threading `recommended` through happens entirely inside the existing pure function rather than requiring new plumbing in the screen.
- The decision-history "nothing differs" and gap-note states reuse the existing `decisions-entry__gap-note` CSS class rather than adding new styling, consistent with `design-reference.md`'s restraint on this screen.
